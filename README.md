# Вектор — AI-ассистент для команды

FastAPI, PostgreSQL 17, SQLAlchemy 2, Alembic и отдельный worker генерации.
FastAPI также раздаёт статический интерфейс. Чаты хранятся в PostgreSQL и доступны
после входа с любого браузера. Реальные ответы даёт OpenAI-совместимый API.

## Устройство

- `users` — учётные записи, Argon2-хеши паролей, состояние доступа.
- `login_sessions` — хеши случайных токенов сессий и срок действия; сам токен только в HttpOnly-cookie.
- `conversations` — диалоги с владельцем, названием и датами.
- `messages` — сообщения пользователя и ассистента, включая контекст вопроса.
- `generations` — сохранённые запросы к модели, их статусы, результаты и ошибки.
- `rate_buckets` — общие для всех процессов лимиты обращений.
- `worker_heartbeats` — состояние обработчиков очереди для readiness-проверки.

API записывает вопрос и задачу генерации в одной транзакции и возвращает `202`.
Worker берёт задачу из PostgreSQL, вызывает модель и атомарно сохраняет ответ
с сообщением. Браузер опрашивает состояние запроса. Закрытие вкладки не отменяет
принятую задачу; после повторного входа её состояние загружается из БД.

Передача прежних сообщений ограничена текущим диалогом, десятью успешными
парами вопрос/ответ и общим бюджетом в 24000 символов вместе с новым вопросом
и системным промптом. Полная история остаётся в БД. Неуспешные запросы не
добавляются в контекст модели.

## Возможности

- Вопрос, дополнительный контекст, Markdown-ответ и копирование.
- Четыре сценария: рабочий вопрос, план, итоги встречи, разбор решения.
- Вход/выход, продолжение диалога, последние пять вопросов по всем беседам и загрузка более старых запросов.
- Постраничная загрузка сообщений; удаление отдельного диалога или всех своих диалогов.
- Восстановление истории и обработки после перезагрузки страницы.
- Состояния очереди, генерации и ошибки; повтор после явного сбоя выполняется вручную.
- Ожидание можно остановить; через две минуты оно приостанавливается автоматически.
  При недоступном worker интерфейс сообщает о сохранённом запросе и позволяет проверить
  его состояние позже. Проверка состояния не создаёт новую генерацию.
- Проверка владельца на каждом запросе чтения, продолжения и удаления.

В браузере остаётся только состояние открытой страницы. Чаты и токены не
записываются в localStorage. Демоответов в приложении нет. Предыдущая браузерная
история версии 1 автоматически не импортируется: у этих записей нет подтверждённого
владельца. Новая версия их не читает.

## Настройка и запуск оператором

Приложение не скачивает и не устанавливает системные пакеты. Следующие команды
приведены для самостоятельного запуска.

### Локальная разработка через Docker

1. Скопировать `.env.example` в `.env`.
2. Задать случайный `POSTGRES_PASSWORD` (рекомендуется не менее 24 символов)
   и `OPENAI_API_KEY`. Для пароля БД удобно использовать URL-safe символы.
3. При другом провайдере указать `OPENAI_BASE_URL` и `OPENAI_MODEL`.

```bash
docker compose up --build -d
docker compose exec app python -m app.manage create-user alice --name "Алиса"
```

Пароль пользователя вводится в скрытом интерактивном запросе; требуется 12–256 символов.
После этого открыть **http://127.0.0.1:8000** и войти. Публичной регистрации и
предустановленной учётной записи администратора нет.

Compose поднимает БД, отдельно применяет миграции, затем запускает API и worker.
Порт PostgreSQL на хост не публикуется. Данные находятся в named volume `postgres_data`.
Обычный `docker compose down` сохраняет его; `down -v` удаляет данные.

### Запуск без Docker при уже доступной PostgreSQL

В `.env` указать `DATABASE_URL` формата `postgresql+psycopg://...`, origin и ключ модели.
Python 3.12+ и uv должны быть установлены заранее.

```bash
uv sync --frozen
uv run alembic upgrade head
uv run python -m app.manage create-user alice
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000
# В отдельном терминале:
uv run python -m app.worker
```

## Работа с моделью и повторными запросами

Клиент использует `POST /chat/completions`, сообщения `system/user/assistant`
и `max_completion_tokens`. Провайдер должен поддерживать этот контракт.
API-ключ передаётся только worker'ом и не возвращается клиенту.

Каждой отправке соответствует UUID `request_id`. Повтор с тем же ID и теми же
данными возвращает сохранённое состояние; с другими данными — `409`. Этот ID
используется и при повторе после потери HTTP-ответа. Для нового запроса после
сохранённой ошибки клиент создаёт новый ID.

На один диалог допускается одна активная генерация: ограничение обеспечивается
частичным уникальным индексом БД. PostgreSQL-блокировки и транзакции защищают
идемпотентность, приём в очередь и глобальное число одновременно работающих задач
между несколькими экземплярами API/worker.

Если процесс погиб после отправки запроса провайдеру, невозможно достоверно узнать,
был ли он оплачен и завершён. После истечения lease задача получает `failed/interrupted`.
Скрытого повторного вызова модели нет: решение о новой генерации принимает пользователь.
При штатном SIGTERM worker дожидается уже взятых задач.

## Доступ и ограничения

- Argon2, серверные сессии с ограниченным сроком, отзыв при выходе и смене пароля.
- `HttpOnly`, `SameSite=Strict`, `Secure` для production-cookie; CSRF-токен в памяти
  страницы и проверка Origin для изменяющих запросов.
- Общие лимиты входа по IP и логину, лимиты генераций на пользователя в минуту/сутки,
  ограничение очереди и глобальной конкурентности через PostgreSQL.
- Не более 6000 символов вопроса, 12000 контекста и 96 KiB тела HTTP-запроса.
- Пул соединений, таймауты БД и LLM, запрет редиректов API-провайдера.
- Сырой HTML из модели отображается как текст. Поддерживается ограниченное
  подмножество Markdown: заголовки, простые списки, цитаты, код, ссылки и выделения.
- CSP и TrustedHost; API-документация выключена в production.
- Логи запросов содержат request ID, путь, статус и время, без тела, cookie и ключей.

Роли администратора и общей командной истории в веб-интерфейсе нет: доступ выдаётся
CLI, каждый пользователь видит свои диалоги. SSO и разделяемые рабочие пространства
требуют отдельной продуктовой модели доступа.

## API

- `POST /api/auth/login`, `GET /api/auth/me`, `POST /api/auth/logout`.
- `GET /api/config` — публичные настройки для вошедшего пользователя.
- `POST /api/ask` — создать задачу; поля `request_id`, `question`, `context`, `mode`,
  необязательный `conversation_id` для продолжения беседы.
- `GET /api/requests/{id}` — `pending`, `running`, `succeeded` или `failed`.
- `GET /api/history?limit=5&before={request_id}` — последние вопросы текущего пользователя.
- `GET /api/conversations?limit=5&offset=0` — список своих диалогов.
- `GET /api/conversations/{id}?limit=50&before={generation_id}` — страница истории.
- `GET /api/conversations/{id}?through={generation_id}` — история до выбранного запроса включительно.
- `DELETE /api/conversations/{id}`, `DELETE /api/conversations` — удаление с каскадом.
- `GET /api/health` — жив ли процесс; `GET /api/ready` — доступна ли БД и есть ли worker.

Все операции с диалогами требуют сессии; изменения дополнительно требуют
`Origin: <PUBLIC_ORIGIN>` и `X-CSRF-Token` из `/api/auth/me`. Ошибки имеют формат
`{"error":{"code":"...","message":"..."},"request_id":"..."}`.

## Проверки для самостоятельного запуска

```bash
uv sync --frozen --group dev
uv run pytest tests/unit -q
npm ci
npm test
```

Интеграционные и браузерные тесты используют **настоящую PostgreSQL**, а не SQLite.
Нужно явно задать `TEST_DATABASE_URL` на отдельную БД с именем `vector_test*`.
Роль должна иметь право создавать временные тестовые БД. Каждый сценарий получает
новую БД с миграциями; после завершения она удаляется. Рабочую БД указывать нельзя.

```bash
uv run pytest tests/integration -q
# При заранее установленном Chromium для Playwright:
npm run test:e2e
```

Без `TEST_DATABASE_URL` PostgreSQL-тесты пропускаются, browser runner завершается
с сообщением о недостающей настройке. Тестовый HTTP-провайдер находится только
в `tests/`, не входит в Docker-образ и не доступен как режим приложения.

Проверки покрывают миграции, транзакционное сохранение, изоляцию владельцев, CSRF,
конкурентную идемпотентность, лимиты, каскадное удаление, восстановление статусов,
контекст диалога и браузерные сценарии. В этой итерации они написаны, но **не запускались**.

## Файлы

`app/routes.py` — HTTP API; `chat_service.py` — транзакции и очередь;
`worker.py` — обработка; `models.py` — схема; `security.py` — доступ;
`migrations/` — версия схемы; `app/static/` — интерфейс;
`compose.yaml` — сервисы PostgreSQL, FastAPI, worker и migrate;
`scripts/backup.sh` — резервная копия по явной команде оператора.
